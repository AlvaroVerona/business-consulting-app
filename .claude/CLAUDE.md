# Business Consulting App

AI-powered business consulting/strategy-analysis macOS app. Full spec: `../CLAUDE_CODE_BUSINESS_CONSULTING_SPEC.md`. Discovery notes, architecture rationale, and decisions log: `../DISCOVERY.md`.

## Stack

- `App/` — SwiftUI macOS app (Swift Package Manager executable, Swift 6 strict concurrency).
- `sidecar/` — Python/FastAPI backend. Owns persistence (SQLite via SQLAlchemy), document ingestion, LLM orchestration. The Swift app is a thin client over `http://127.0.0.1:8765`.

## Non-negotiable rules (spec sections 5 and 13)

1. Every conclusion is a `Finding`: FACT | CALCULATION | INFERENCE | HYPOTHESIS | ASSUMPTION (`sidecar/src/schemas/evidence.py`). Never bare prose.
2. Citations must reference a real `chunk_id`/`document_id` from that project's ingested documents — never fabricated. `services/evidence_validation.py:validate_evidence_citations` enforces this with a retry loop (used by every LLM-evidence-producing service: QuickAnswerService, BusinessUnderstandingAgent, ...); don't weaken it.
3. Arithmetic belongs in Python, not in an LLM's head. **A local smoke test on 2026-08-19 caught llama3.1 making a real arithmetic error** (computed a gross-margin percentage off by ~3.5% relative) inside a `CALCULATION`-typed finding it otherwise formatted correctly. The JSON contract and citation validation worked; the arithmetic didn't. Phase 2 built `sidecar/src/analysis/financial.py` + `period_extractor.py` (deterministic, no LLM) to fix this — verified live: with the engine's numbers injected into Quick Answer's prompt as "ALREADY-COMPUTED FINDINGS", llama3.1 correctly reused the exact deterministic values instead of recomputing. That same smoke test also caught a second, subtler bug: the first prompt format listed each engine finding as `finding_id=9 chunk_id=1 ...`, and the model sometimes cited the `finding_id` as if it were `citation.chunk_id`. Fixed by dropping `finding_id` from the prompt entirely (see `_build_prior_findings_context` in `quick_answer_service.py`) — a `Finding.origin` column ("engine" vs "llm") is what makes the entries in this prompt section trustworthy.
4. LLM backend is hybrid: local Ollama (`llama3.1`) by default, Claude API only on a caller's explicit per-call opt-in (`sidecar/src/llm/router.py`). Never make Claude the silent default.

## Running it

```bash
cd sidecar && uv sync --extra dev && uv run uvicorn src.main:app --reload --port 8765
cd App && swift run
```

Tests: `cd sidecar && uv run pytest`.

## Phase 2 status (2026-08-19)

Built: deterministic financial engine (`analysis/financial.py`, `period_extractor.py`, `financial_analysis_service.py`) computing gross margin, EBITDA margin (implied when not reported), opex ratio, and cross-period trends from ingested CSV/XLSX rows via column-name heuristics (no LLM). Only genuinely new/changed numbers create new Finding rows.

## Phase 3 status (2026-08-19)

Built the full Deep Analysis pipeline (`services/deep_analysis_orchestrator.py`, spec section 2/15): `BusinessUnderstandingAgent` (LLM, same evidence-citation contract as Quick Answer) → `FinancialAnalysisService` → `ConcernDetectionService`/`OpportunityDetectionService` → `HypothesisManagerAgent` (LLM, one root-cause-hypothesis batch per concern, **forces every generated hypothesis to status=PLAUSIBLE regardless of what the LLM proposes** — an untested hypothesis cannot self-assign CONFIRMED) → `QualityReviewerService` (deterministic: flags unsupported claims, double counting, unevidenced hypothesis statuses) → `ExecutiveSynthesizerService` (LLM, spec section 11's format, `concern_ids`/`opportunity_ids` validated against what's real for the project). Persisted as `DeepAnalysisRun` (status RUNNING/COMPLETED/FAILED).

BusinessUnderstandingAgent's failure degrades the run (continues with `business_profile=None`) rather than aborting it — the deterministic steps below don't depend on it. ExecutiveSynthesizerService's failure does mark the whole run FAILED, since without it there's no useful output.

Verified live end-to-end against local `llama3.1` (a wine-bar memo + a 3-month declining-margin P&L): correct business profile extracted from the narrative memo, correct concern/hypothesis/synthesis linkage, all citations valid, zero quality issues flagged, ~50s total for the full 3-LLM-call pipeline (business understanding → hypotheses → synthesis) — no retries needed on this run, though the retry paths are unit-tested since local-model reliability is not guaranteed run to run (see the Phase 1/2 arithmetic and citation-conflation bugs above).

Deliberately deferred (see spec section 15 phasing): issue-tree construction (MECE decomposition — genuinely needs its own focused pass, not a stub), true parallel multi-agent execution (current pipeline is sequential, matching `agent-platform`'s proven pattern), and a qualitative LLM-based pass in QualityReviewerService (current version is deterministic/mechanical checks only).

Shared helper extracted this phase: `services/evidence_validation.py:validate_evidence_citations` — QuickAnswerService and BusinessUnderstandingAgent both had near-identical citation-validation logic; factored out before it could drift.

Two real bugs caught by generating an actual PDF from live Deep Analysis output (not just unit tests) and reading it:
1. The 90-Day Action Plan and Business Performance tables used plain strings as reportlab `Table` cell content, which does not reliably word-wrap within a fixed column width — long LLM-authored text visibly overlapped adjacent cells. ## Issue trees (2026-08-19) — MVP DoD is now 13/13

Built as its own focused pass, per the note above. `IssueTreeService` (LLM, `services/issue_tree_service.py`) decomposes a **user-provided** question into a tree, 2 levels deep (matches the spec's own Revenue→Price/Volume/Mix example) — deliberately NOT auto-triggered from a detected Concern's title. Spec section 2's workflow treats "define the key question" (step 3) as its own deliberate step before "build issue tree" (step 4); guessing a question from a concern title would produce a weaker tree than one the user actually means to investigate, and risks polluting Deep Analysis's automatic pipeline with a weak artifact nobody asked for.

Nodes carry `is_forced_mece`/`overlap_note` — the spec's explicit escape hatch ("do not force MECE structures where the underlying business reality does not support them; explicitly flag overlap or uncertainty," section 4). Verified live against real `llama3.1`: asked "Why did EBITDA decline this quarter?", got a correct 2-level MECE breakdown (Revenue Mix, Price Realization, Operating Expenses) *and* correctly flagged "Interest Expense" as `is_forced_mece=true` with the overlap explained ("Bundled with Operating Expenses") — the model used the escape hatch appropriately on the first attempt, not just when the retry loop forced a correction.

Persisted flat (`IssueNode.parent_id`, self-referential FK) and reassembled into nested JSON server-side (`routes.py:_issue_nodes_to_out`) — no ORM self-referential relationship, kept simple since nothing needs eager-loaded children. `POST /projects/{id}/issue-trees` (accumulates — unlike Concern/Opportunity's clear-and-replace, a project can have multiple issue trees for different questions over time, so nothing is deleted on a new one). SwiftUI: `IssueTreeView`, a question field + `OutlineGroup` rendering (needed `IssueNode.nonEmptyChildren: [IssueNode]?` since OutlineGroup treats nil, not empty array, as "leaf"). `IssueTree`/`IssueNode` needed explicit `Sendable` conformance — Swift 6's automatic synthesis didn't infer it for the self-referential-via-array struct, unlike every other flat model in this codebase.

Caught and fixed by my own tests before this ever hit a live model: `_validate_depth`'s exceeded-depth check fired even on an empty `children: []` list at depth+1, rejecting perfectly valid 2-level trees. Fixed by returning early when `nodes` is empty, before checking depth.

Fixes from a medium-effort code review before this commit:
- `ProjectViewModel.buildIssueTree()` had no re-entrancy guard — the TextField stays enabled while a build is in flight (only the Button swaps for a spinner), so a second Return press fired a duplicate POST. Added `guard !isBuildingIssueTree else { return }`.
- Depth was validated but sibling count wasn't — a model returning e.g. 20 top-level branches would've passed straight through. Added `_validate_branching` with a generous ceiling (`MAX_SIBLINGS = 8`, above the prompt's stated 2-5/4 guidance) that only catches genuinely degenerate output, not minor overshoots.
- **The serious one**: `create_issue_tree`/`create_issue_node` committed per row inside `IssueTreeService`'s recursive persist loop — a mid-tree failure left a permanently truncated tree durably saved with no way to detect or repair it. Fixed: both now `flush()` instead of `commit()` (needed so a child's `parent_id` can reference its just-created parent within the same transaction), and `IssueTreeService.run()` calls a new `Repository.commit()` once at the very end, with `Repository.rollback()` on any exception — a flushed-but-uncommitted row is still visible to queries on the same session, so skipping the final commit alone isn't sufficient; the explicit rollback is what actually discards partial work. Regression-tested by monkeypatching `create_issue_node` to fail on the 2nd node and asserting nothing at all was persisted.
- `GET /projects/{id}/issue-trees` called `list_issue_nodes` once per tree (N+1) — real given issue trees accumulate and are never cleared, unlike Concern/Opportunity. Added `Repository.list_issue_nodes_for_project` (one query, grouped by `tree_id` in the route) — O(1) queries regardless of tree count.
- The generate/parse/retry control flow was duplicated near-identically across `QuickAnswerService`, `BusinessUnderstandingAgent`, `HypothesisManagerAgent`, `ExecutiveSynthesizerService`, and now `IssueTreeService` — the same category of duplication this project already factored out once (`services/evidence_validation.py`, this same changelog, Phase 3). Extracted `llm/retry.py:generate_json_with_retry(llm, label, max_retries, build_prompt, parse)` and migrated all 5 call sites (`HypothesisManagerAgent` keeps its per-concern "return `[]` instead of raising" tolerance by catching the harness's `ValueError` at the call site, not inside the harness). Re-verified live against real `llama3.1` after the refactor: full Deep Analysis pipeline, issue tree generation, and Quick Answer all still work correctly end-to-end — not just the 131-test suite passing unchanged.

## App packaging (2026-08-19)

Until now the only way to run the macOS app was `swift run` from Terminal — no real `.app`, no icon, not launchable from Finder/Spotlight. This project deliberately isn't an Xcode project (`../DISCOVERY.md`'s architecture rationale), and there's no GUI-Xcode access in this environment to convert it into one, so app bundling had to happen via a hand-written script rather than Xcode's built-in "Archive" flow — the standard approach for indie SwiftPM-based macOS apps.

`App/Scripts/build-app.sh`: `swift build -c release`, then assembles `BusinessConsultant.app` (`Contents/MacOS`, `Contents/Resources/AppIcon.icns`, `Contents/Info.plist`) and ad-hoc code-signs it (`codesign --sign -` — local use only; real notarization needs an Apple Developer account, out of scope here). Output lands in `.build/app/` (already gitignored).

Icon: generated natively via AppKit rather than sourced from anywhere (`App/Scripts/generate_icon.swift`, run once — draws a rounded-square gradient with a white `chart.line.uptrend.xyaxis` SF Symbol at every required `.iconset` size, then `iconutil -c icns`). The generated `AppIcon.icns` is committed (`App/Resources/`); the script re-runs only if the design changes.

One real bug during this pass, caught immediately on the first run: the build script's own `echo` strings used a Unicode ellipsis character (`…`) interpolated right after `$BUNDLE_NAME` with no separating whitespace — bash's variable-name parsing in the shell's locale treated the ellipsis's raw UTF-8 continuation bytes as part of the variable name, producing `unbound variable` errors that only reproduce with that literal byte sequence. Fixed by using plain `...` (ASCII) instead — not just working around a one-off typo, but a reminder that shell scripts shouldn't interpolate non-ASCII characters directly adjacent to a variable reference regardless of terminal/editor encoding assumptions.

Verified live: `open .build/app/BusinessConsultant.app` launches the bundled app (not `swift run`) as its own process, and it talks to the sidecar exactly as before.

## Auto-launching the sidecar (2026-08-19)

Requested follow-up: the packaged app still needed the sidecar started manually in a separate Terminal — not a real double-click launch. `SidecarLauncher.swift` (`@MainActor @Observable`, singleton): on app launch, check `SidecarClient.isHealthy()` (new `GET /health` check); if nothing answers, spawn `uv run uvicorn src.main:app --port 8765` via `Process`, `currentDirectoryURL` pointed at a fixed sidecar path (`~/Documents/ai_for_business/business-consulting-app/sidecar`, overridable via `BUSINESS_CONSULTANT_SIDECAR_PATH`) — a fixed path is an acceptable trade-off since this is a personal, single-machine tool (README, ad-hoc signing note), not solving for "this app on someone else's machine." `uv`'s path is resolved by checking known install locations directly (`~/.local/bin/uv`, `/opt/homebrew/bin/uv`, `/usr/local/bin/uv`), not via `PATH` lookup — a GUI-launched app doesn't inherit the login shell's `PATH` (no `.zshrc`/`.bash_profile` sourcing), so `Process` wouldn't find `uv` the way Terminal does. `BusinessConsultantApp` shows a small "Starting local backend..." loading screen (`SidecarLaunchView`) while this runs, then proceeds to the normal UI regardless of outcome — a slow/failed start surfaces later as ordinary per-request errors, not a blocking app-launch failure.

Two real bugs, both caught by testing the actual quit flow live (not assumed from reading the code), before considering this done:

1. **Sidecar survived quitting the app.** `applicationWillTerminate` called `SidecarLauncher.shared.shutdown()` inside `Task { @MainActor in ... }` — an unstructured Task that isn't guaranteed to run before the process actually exits (`applicationWillTerminate` returning doesn't wait for it, and NSApplication's termination sequence continues immediately). Reproduced: quit the app via `osascript ... to quit`, and the sidecar process was still alive and serving requests afterward — `shutdown()` had simply never executed. Fixed by calling it directly and synchronously (`NSApplicationDelegate` callbacks run on the main actor already, so no `Task`/`await` is needed).

2. **Even with shutdown() actually running, the sidecar still survived** — `process.terminate()` only signals the single PID Foundation launched (`uv`), but `uv run uvicorn` spawns uvicorn as its own child process in the *same process group*, and `uv` doesn't reliably forward SIGTERM to it. Reproduced via `ps -o pid,ppid,pgid`: the `uv` and `uvicorn` processes shared one process group, and terminating just the `uv` PID left `uvicorn` running as an orphan (reparented to launchd) after the app fully quit. Fixed by resolving the actual process group (`getpgid`, not assumed to equal the child's PID) and signaling the whole group (`kill(-pgid, SIGTERM)`, escalating to `SIGKILL` after a brief wait if still alive).

Verified live, both directions: (a) cold launch with no sidecar running — app spawns it, health check succeeds, quitting the app terminates *both* the `uv` and `uvicorn` processes; (b) sidecar already running manually before the app launches — app detects it via the health check and does not spawn a duplicate, and quitting the app leaves the manually-started sidecar untouched (since `didLaunchSidecar` is only set when this instance did the spawning).

Third fix, from a medium-effort code review: two near-simultaneous launches (Dock + Spotlight, or a quick relaunch) could both observe "not healthy yet" and both attempt to spawn a sidecar, racing for port 8765 — the loser's `uvicorn` crashes on bind and that instance shows a misleading "taking longer than expected" instead of just waiting for the winner. Added an atomic file lock (`O_CREAT|O_EXCL`, not check-then-create, which would reintroduce the same race) so only one concurrently-launching instance actually spawns; the rest wait and poll. The lock file stores the owning process's pid and is treated as stale (and reclaimed) if that process is no longer alive (`kill(pid, 0)`), so a crash between acquiring and releasing it doesn't permanently wedge future launches. Verified live: `open -n` twice back-to-back (forcing two genuinely separate app processes, since a normal second `open` on a running app just activates the existing instance) produced exactly one `uv`/`uvicorn` process pair, not two racing for the port.

Also confirmed (not a bug, a test-methodology note): raw `kill -TERM` on the app process does *not* trigger `applicationWillTerminate` — AppKit's termination lifecycle runs off the Cocoa "quit" Apple Event (Cmd+Q, Dock "Quit", `osascript ... to quit`), not POSIX signals, so a hard `kill` bypasses the sidecar-shutdown hook entirely. This matches how every AppKit/SwiftUI app behaves, not something specific to this one; testing shutdown behavior needs a real quit event, not `kill`.

## First real-scenario live test: Fermento (2026-08-20)

Every prior verification in this project was either a hermetic unit test or a small synthetic smoke test. This pass ran the whole stack — ingestion, the deterministic financial engine, concern/opportunity detection, and the full Deep Analysis pipeline against real `llama3.1` — against a deliberately non-trivial fictional scenario: a two-founder natural-wine bar in Malasaña, Madrid, with a real narrative (supplier delays, spoilage waste, seasonal effects), 6 months of P&L, and a 16-wine international list. Fixture committed at `manual-tests/fermento-winebar/` (memo, financials, wine list, plus a README with exact replication steps) specifically so this is a re-runnable regression scenario, not a one-off.

This surfaced **3 real bugs**, all fixed with regression tests and re-verified live against the actual running sidecar (not just pytest):

1. **`period_extractor.py` only recognized Latin American Spanish COGS terms.** `coste_ventas` (the term used in Spain) matched nothing in `_ALIASES["cogs"]` — only `costo_de_ventas`/`costo de ventas` did. This silently dropped every period from a Madrid business's own financials (the `"period" not in matched or revenue is None or cogs is None"` skip in `extract_periods`). Added `coste_ventas`/`coste de ventas`/`coste_de_ventas` as aliases.

2. **Concern/opportunity detection was blind to non-monotonic material trends.** `classify_trend()` only returns `"declining"`/`"improving"` for a *strictly* monotonic series — Fermento's revenue and gross margin rose March→May, then fell hard through August, so `classify_trend` correctly labeled both `"mixed"`. But `_margin_compression`/`_revenue_decline` (concern) and the opex-efficiency check (opportunity) gated on an exact `== "declining"`/`== "improving"` match *before* ever reaching the materiality-threshold check that's supposed to be the real filter — so a 13-point gross margin drop and a 38% revenue decline produced **zero concerns**. A rise-then-fall shape is an extremely common real-business pattern (almost every business has some early ramp-up variance), so this wasn't an edge case. Fixed by widening the accepted set to `{"declining", "mixed"}` / `{"improving", "mixed"}` in `concern_detection_service.py`/`opportunity_detection_service.py` — the materiality check downstream still correctly excludes `"stable"`/wrong-direction cases, including the one existing test (`test_resolved_concern_recorded_when_it_no_longer_recurs`) that manually overrides `trend` to simulate resolution without changing the underlying data.

3. **Citation validation checked chunk_id and document_id independently, not as a pair.** `BusinessUnderstandingAgent`'s generated profile cited `document_id=3, chunk_id=1` as a FACT — but chunk_id 1 actually belongs to document_id=1 (confirmed directly against `document_chunks` in the running sidecar's SQLite DB). Each half was independently valid (chunk 1 exists; document 3 exists), so `validate_evidence_citations`'s old two-independent-sets check let the fabricated pairing straight through into a FACT-typed finding — exactly the evidence-integrity violation spec section 13 exists to prevent, and a new failure mode beyond the "finding_id-cited-as-chunk_id" confusion bug from Phase 3. Fixed by changing the signature to `chunk_document_ids: dict[int, int]` (chunk_id → its real document_id) and checking the pairing when both are cited; new `tests/test_evidence_validation.py` (6 tests, previously no dedicated test file existed for this shared function) covers it directly, not just indirectly through the two call sites.

Code review (medium effort) on all three fixes: no findings.

**Two things found but not fixed — flagged for a decision, not silently left as-is:**

- `HypothesisManagerAgent`'s prompt (`hypothesis_manager_agent.py`) only includes the triggering Concern's `title`/`business_impact`/`what_would_change_conclusion` — it never sees any document content, the BusinessProfile, or raw chunks. Live result: all 6 generated hypotheses for Fermento were generic industry boilerplate ("shift in market demand", "decline in a major customer's orders") with zero connection to what the memo actually documents in detail (supplier lead times, opened-bottle spoilage, cut hours). This is an architectural gap — grounding hypothesis generation in the project's actual evidence — not a small patch, and wasn't attempted this pass.
- `BusinessUnderstandingAgent`'s output on this run was a near-total hallucination: it described Fermento as a wine *producer* ("vineyard maintenance", "winemaking equipment", "wine clubs", "global market") despite the actual Spanish-language memo (clearly describing a wine *bar*) being fully present in its prompt context — confirmed by inspecting the prompt template, not assumed. This looks like a local-model (llama3.1, 8B, quantized) capability limitation on a longer Spanish-language narrative rather than a code defect; worth comparing against `useClaude=true` before concluding anything further.
- Separately noticed, not yet investigated as a bug: `QuickAnswerService.answer()` calls `repo.create_finding` unconditionally for every evidence item on every call, with no dedup by statement text — unlike `FinancialAnalysisService.run()`, which is explicitly idempotent for this reason (Phase 2 changelog entry above). Repeated Quick Answer questions touching the same numbers will keep creating duplicate `Finding` rows with `origin="llm"`.

## Live-found bug: Python literals break every retry, plus a real UX gap (2026-08-20)

Álvaro hit a real error live in the packaged app and couldn't copy the error text out to report it — two separate problems, both fixed.

**Root cause (sidecar)**: a Quick Answer question 502'd. `/tmp/fermento_sidecar.log` showed `extract_json` failing identically on all 3 retry attempts for the same request — `llama3.1` had emitted Python's `None` instead of JSON's `null` in a citation field (`{"chunk_id": None}`), which `json.loads` rejects. Confirmed this isn't a one-off: the model made the exact same mistake on every retry, so the existing retry loop could never recover on its own. Fixed in `llm/json_utils.py`: `extract_json` now normalizes bare `None`/`True`/`False` tokens to `null`/`true`/`false` before parsing — but only outside string literals, so real content that happens to contain those words (e.g. "None available") is untouched. Reproduced the exact failing payload from the log and confirmed it now parses; added regression tests in `test_json_utils.py`. Re-verified live: the same question that 502'd now returns 200.

A medium-effort code review caught that this introduced a second string/escape-tracking loop duplicating the one `extract_json`'s brace-matcher already had — refactored both into a shared `_iter_outside_strings` generator so there's exactly one place that understands "am I inside a JSON string right now."

**The actual UX gap (Swift)**: the underlying reason Álvaro couldn't paste the error here at all — macOS's native `.alert()` renders its message via NSAlert, and NSAlert text has never been selectable, `.textSelection()` included, since it isn't SwiftUI-drawn text at all. Replaced both `.alert()` error displays (`ContentView.swift`, `ProjectWorkspaceView.swift`) with a new `CopyableErrorSheet.swift` — a plain `.sheet()` with selectable, monospaced error text and an explicit Copy button (`NSPasteboard`). Also added `.textSelection(.enabled)` so answers/findings/concerns/etc. are selectable throughout the app, not just error text.

First attempt at the selectable-text change applied `.textSelection(.enabled)` too broadly — at the `NavigationSplitView`/`NavigationStack` level, which also wraps each screen's `.toolbar`. A medium-effort code review caught the real risk: on macOS, an ancestor `.textSelection(.enabled)` can make a `Button`'s text-based label compete with click-to-select, e.g. `SidebarView.swift`'s project-switcher buttons (`Button { ... } label: { Label(project.name, ...) }`) or `ScenarioView.swift`'s Form containing a `Picker` and three `Slider`s. Re-scoped precisely instead of guessing it was probably fine: `.textSelection(.enabled)` now sits only on the actual content subtree in each view (the `VStack` inside a `ScrollView`, or a specific `Section`), never on anything that also carries a `.toolbar` or an interactive control — verified file-by-file which `Button`s use icon-only labels (`Image`, safe) vs. text labels (`Label`/`Text`, risky) before deciding where it was safe to apply.

## Live-found bug: "the request timed out" (2026-08-20)

Álvaro hit this immediately after the previous fix, on the very same kind of call (Quick Answer). Root cause was on the Swift side this time, not the sidecar: `SidecarClient`'s `session = URLSession(configuration: .default)` carries Foundation's default 60s `timeoutIntervalForRequest` for every call except `isHealthy()`'s explicit 1.5s override. Confirmed the sidecar itself has no timeout at all talking to Ollama (`grep -rn "timeout" src/llm/*.py` — nothing), so it was still legitimately working past 60s: the sidecar log showed a `QuickAnswerDraft` validation error (llama3.1 omitted required fields), which triggers a same-request retry (`generate_json_with_retry`, up to 3 attempts total) — and `ps` showed Ollama's `llama-server` subprocess had only just started around the same time, meaning a cold model load was likely stacked on top of that retry. Deep Analysis was already measured at ~50s with zero retries needed (Phase 3 changelog entry above), so 60s was never going to hold up once any retry was involved.

Fixed by giving `SidecarClient`'s three LLM-backed calls (`askQuickQuestion`, `createIssueTree`: 120s; `runDeepAnalysis`: 300s, being a multi-step pipeline where each step can independently retry) an explicit longer `timeoutInterval`, via a new optional parameter on the private `post()` helper — every other call (CRUD, deterministic financial/scenario endpoints) keeps the 60s session default, since those have no retry loop and no reason to hang. Low-effort code review: no findings.

## Document preview (2026-08-20)

Álvaro asked for a way to preview the input documents from inside the app. New `GET /projects/{project_id}/documents/{document_id}/content` serves the original uploaded bytes (not the parsed/chunked text) with a guessed `Content-Type`; the Swift side downloads them, writes to a temp file preserving the original extension, and renders them via `QLPreviewView` (Quartz/AppKit) wrapped in an `NSViewRepresentable` — native Quick Look handles PDF/CSV/DOCX/MD/XLSX without this app writing its own per-file-type renderer. An icon-only eye button per document row (`DocumentsPanel` in `ProjectWorkspaceView.swift`) opens it in a sheet; deliberately icon-only rather than a text-labeled button, matching the `.textSelection(.enabled)` re-scoping lesson from the copyable-text pass above.

A medium-effort code review of this feature (2 finder subagents + verification, ~230s) found 3 real issues, all fixed and re-verified before this was considered done:

1. **`save_upload` silently overwrote same-named files** (`storage.py`) — a pre-existing bug, but the new preview endpoint made it directly observable for the first time: upload two documents with the same filename to the same project, and the *older* document's preview started showing the *newer* document's content, since both `Document` rows' `storage_path` pointed at the one file left standing on disk. Fixed with Finder-style disambiguation (`pnl.csv` → `pnl (1).csv` → `pnl (2).csv`, looping until a free name is found).

2. **Fixing #1 surfaced a second, more consequential bug**: the test suite has never isolated `sidecar/data/` the way it isolates the database (`conftest.py`'s `_clean_db` autouse fixture resets tables per test, but nothing reset on-disk files) — and since `_clean_db` resets autoincrement IDs too, dozens of test functions across the suite create "project 1" over and over and upload same-named files (`pnl.csv`, `notes.xyz`), all landing in the **real developer's `sidecar/data/1/` directory** alongside actual project data (this session's real Fermento files). Invisible for as long as `save_upload` silently overwrote collisions; once it started disambiguating instead, `test_storage.py`'s exact-path assertion broke — and inspecting `sidecar/data/1/` directly showed it littered with `pnl (1).csv` through `pnl (10).csv` next to `memo_fermento.md`/`financiero_fermento.csv`/etc. Cleaned the real directory back to just the Fermento files, then fixed the actual root cause: a new `_isolated_data_dir` autouse fixture in `conftest.py` monkeypatches `storage.DATA_DIR` to a fresh, pytest-managed `tmp_path` per test — mirroring `_clean_db`'s isolation for the DB. `test_storage.py` had to change `from src.storage import DATA_DIR` (binds at collection time, before the fixture patches anything) to a module reference (`storage_module.DATA_DIR`, resolved fresh at assertion time) to actually observe the patched value.

3. **TOCTOU between an `os.path.exists` check and `FileResponse` opening the same path** — `FileResponse` defers actually opening the file until Starlette streams the response body, after the route function has already returned, so a file removed in that window would 500 instead of 404. Switched to a direct synchronous read (matching the existing `reports/pdf|pptx|excel` endpoints' `Response(content=...)` pattern) so a `FileNotFoundError` happens inside the route function where it can actually be caught.

Also fixed, same review: `DocumentPreviewSheet.swift`'s temp-file cleanup only ran in `onDisappear` against whatever `localFileURL` held at that instant — if the download finished *after* the sheet was dismissed, the write and state-set happened after `onDisappear` had already fired with nothing to clean up, leaking the temp file. Added a `Task.isCancelled` check both before writing and right after, since `.task` cancellation is cooperative and isn't observed automatically after an `await` returns.

## Live-found bug: the app can't do simple arithmetic on totals (2026-08-20)

Álvaro asked why the app "doesn't seem able to do simple sums/subtractions" when he asked for total OPEX or total COGS. Verified live, and it was worse than "can't do arithmetic": asking Quick Answer for total OPEX (real answer: 14,850.00, computed independently in a plain Python one-liner from the CSV) got back **4,770** — the model had used the wrong formula entirely (`revenue - cogs`, which is gross profit, not opex, not even the right concept), its own shown subtraction for each month didn't match the number it reported for that month, and the final total didn't match the sum of its own reported monthly figures either. Three independent layers of wrong, not one.

Root cause: `analysis/financial.py`/`financial_analysis_service.py` computed every *per-period* metric deterministically (that's the whole reason this file exists — spec section 13, and the Phase 2 changelog entry above about the original ~3.5% arithmetic error), but never a *cross-period sum*. So when a question needed one, there was no engine Finding to reuse, and QuickAnswerService's LLM had to sum 6 rows itself from raw context — exactly the kind of multi-step arithmetic this whole architecture exists to keep out of the LLM's hands.

Fixed: `FinancialAnalysisService._persist_totals_findings` (new) computes total revenue/COGS/opex/EBITDA across every ingested period in plain Python, persisted as `origin="engine"` CALCULATION Findings alongside the existing per-period ones — same idempotency-by-statement-text mechanism as everything else in this file. Re-verified live: the same question that returned 4,770 before now returns 14,850.00, citing the engine finding directly instead of recomputing.

A medium-effort code review (2 finder subagents, ~160s) reproduced two further real bugs before this was considered done, both fixed and regression-tested:

1. **The fix could silently fail to fire on a larger project.** `_persist_totals_findings` runs *before* the growth/trend findings within `run()`, so totals get an *earlier* `created_at` — and `repository.list_findings` orders newest-first. On a project with many periods (reproduced directly with 60 monthly periods → 185 engine findings), the totals findings sorted past `QuickAnswerService`'s `engine_findings[:MAX_CONTEXT_CHUNKS]` (60) slice and never reached the LLM's prompt at all, silently reproducing the exact bug this whole change exists to prevent. Fixed by prioritizing totals findings unconditionally in `_build_prior_findings_context` — they're always few (≤4) and always listed first, so volume elsewhere can never crowd them out. Verified the regression test actually catches this: reverted the fix, confirmed the test failed, restored it.
2. **The stated date range could be wrong.** `_persist_totals_findings` labeled every total's range using the overall period list's first/last, even when the summed field was missing from the first or last period — reproduced directly: Jan (no opex), Feb+Mar (opex reported) produced "Total opex from Jan to Mar (2 periods)", which quietly includes a month that was never in the sum. Fixed by deriving the range from the periods that actually have the field, not the project's overall period list.
